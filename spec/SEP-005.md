# SEP-5: Evidence Batching

Status: draft · Editor: SigmaUno project maintainers

## Purpose

Aggregate commitments and provide deterministic inclusion witnesses.

## Design requirements

Candidate RFC 6962-style construction uses distinct leaf/node prefixes, ordered leaves, and explicit leaf index and tree size. Preserve exact manifest bytes and bind root, algorithm, count, and version. Public IDs must be non-identifying and generated by the system.

## Decisions required before implementation stability

Define exact leaf preimage, empty-tree behavior, odd-sized tree construction, proof serialization, and manifest-to-provider binding. Publish vectors for size 1 and non-power-of-two trees, reordered leaves, truncated/extra paths, and wrong index/count. A root string alone does not authenticate the rest of a manifest.

## Acceptance

Publish precise byte-level rules, independent positive and negative test vectors, compatibility behavior, and security considerations. Review before marking this draft stable.

## Implementation experiment

The [Merkle primitive](../pkg/proof/merkle/README.md) now implements RFC 6962 roots and paths with reproducible Python/Go fixtures. The commitment and manifest experiments below now define candidate entry/manifest bytes for review. The outer package, path serialization, service behavior and external review remain pending #2/#4. The primitive accepts raw entry bytes and must not be passed a leaf hash as though it were an entry.


## Experimental manifest profile 1 — proposed for review

[Batch implementation](../pkg/proof/batch/README.md) and [Python-generated vectors](../pkg/proof/batch/testdata/sep5-draft.json) implement this proposal. It is not a stable interoperable release. Require review before production evidence; incompatible changes require a new profile version.

A leaf entry is exactly the raw 32-byte commitment from SEP-2 profile 1, not its hexadecimal text, private preimage or document digest. Apply the RFC 6962 `00` leaf prefix exactly once; node hashes use `01` followed by left and right 32-byte child hashes. Preserve insertion order, including duplicates. A duplicate commitment does not prove a unique occurrence from its bytes alone; ingestion idempotency is a separate service responsibility.

Use RFC 6962 splitting at the greatest power of two strictly below the subtree size; do not duplicate odd leaves. Paths list siblings from leaf to root, with zero-based index and tree size supplying directions. The generic primitive supports an empty root, but this batch profile rejects empty batches. This proposal caps batches at 65,536 leaves (maximum path depth 16) to bound construction and witness size. Service defaults may be smaller; the limit is not a performance claim.

The public manifest is exactly 61 bytes:

| Offset | Length | Field | Accepted value |
| --- | --- | --- | --- |
| 0 | 17 | Domain | ASCII `sigmaproof:batch` followed by byte `00` |
| 17 | 1 | Manifest version | `01` |
| 18 | 1 | Commitment profile | `01` = experimental SEP-2 profile 1 |
| 19 | 1 | Commitment algorithm | `01` = SHA-256 |
| 20 | 1 | Tree algorithm | `01` = RFC 6962 SHA-256 |
| 21 | 8 | Leaf count | Unsigned big-endian integer, 1 through 65,536 |
| 29 | 32 | Tree root | Raw SHA-256 tree root |

No padding, optional fields or trailing bytes are accepted. Reject every unsupported version/algorithm and invalid count. A structurally valid root is not necessarily a genuine publication; parsing must not imply authentication. The fixed framing avoids JSON canonicalization and duplicate-key ambiguities in this public payload without choosing the outer package format.

The Celestia adapter must publish these exact bytes as the blob payload and preserve them unchanged in the exported package. Recompute the Celestia commitment from those bytes with the configured namespace/share rules, then verify inclusion and authenticate the header independently. Publishing only the root, or replacing these bytes with a local manifest digest, is not this profile. Network, namespace, share version and anchor trust material belong to the provider receipt and still need their own binding checks.

`SHA-256(encoded manifest)` is a local content address only. Changing the count, root or supported algorithm/version bytes changes the manifest bytes and hence the value that the provider must bind. In particular, some index/path combinations still reproduce the same root under different claimed sizes; successful membership alone does not authenticate size. Verify the exact manifest against external anchor evidence before reporting authenticated publication.

Only count, protocol fields and an opaque root are public. Count leaks batch cardinality; document contents, raw document digests, nonces, private identifiers and timestamps are absent. No extra public batch identifier is needed for this proposal. Commitments must come from randomized SEP-2 creation; their type alone cannot prove correct producer behavior.

Freeze the ordered commitment set and exact manifest bytes transactionally before provider submission. Retries reuse the same bytes. Any changed entry/order/count requires a new batch manifest. Portable inclusion-path serialization and envelope parser limits remain an explicit #4 dependency; the typed Go path API is not a portable file format.
