# SEP-1: Evidence Envelope

Status: draft · Editor: SigmaUno project maintainers

## Purpose

Define portable package serialization, content addressing, resource bounds, extension handling, and immutable revisions.

## Design requirements

Preserve protocol/algorithm IDs, document representation and digests, private nonce, metadata presence/digest, evidence links, batch manifest and path, provider witnesses, trust evidence, and complete policy definitions where used. References must resolve inside the exported bundle for required material. External retrieval is optional enrichment.

## Decisions required before implementation stability

Choose canonical JSON (evaluate RFC 8785) or deterministic binary encoding, byte framing, attachment layout, signature scope, size/depth limits, and unknown-field behavior. Reject duplicate keys and unsupported critical versions. A schema validates structure, not cryptographic authenticity.

## Acceptance

Publish precise byte-level rules, independent positive and negative test vectors, compatibility behavior, and security considerations. Review before marking this draft stable.

## Experimental unanchored package profile 1

Status: implemented for development and review; **not the anchored MVP format**. This narrow profile composes the reviewed experimental commitment and batch encodings without inventing a Celestia witness before #3 passes. It can establish only local document-to-batch consistency. A recipient given a replaced document and a newly constructed self-consistent package cannot establish that either existed earlier.

Use a single binary file with the extension `.sigmaproof`. It contains private material. Do not upload it to a public anchor. The exact format is:

| Offset | Length | Field |
| --- | --- | --- |
| 0 | 8 | ASCII `SIGMAPRF` |
| 8 | 1 | Package profile version `01` |
| 9 | 90 | Exact private SEP-2 commitment preimage |
| 99 | 61 | Exact public SEP-5 manifest |
| 160 | 8 | Unsigned big-endian zero-based leaf index |
| 168 | 1 | Sibling count `n`, 0 through 16 |
| 169 | `32 × n` | Raw sibling hashes, leaf to root |
| `169 + 32 × n` | 1 | Anchor count, which must be `00` in this profile |

Total size is exactly `170 + 32 × n` bytes, bounded to 682 bytes. The index must be smaller than the manifest count. The sibling count must exactly match the RFC 6962 path length derived from index and count; shorter and longer paths are rejected. There is no independent tree size field to disagree with the manifest.

Each embedded preimage/manifest is decoded strictly with its existing domain/version/algorithm/size rules. Unsupported package or embedded profiles and nonzero anchor counts return unsupported, never success. Reject truncation, trailing data, concatenated packages and arbitrary extra fields. There are no JSON maps, duplicate keys, nested structures, archive entries, attachment paths, compression, URLs or external references in this profile; JSON/ZIP inputs are not accepted. Stream readers consume at most 683 bytes to detect oversize inputs, independent of claimed lengths.

Successful decoding establishes only structure. Verification recomputes the randomized commitment from the private witness, checks its inclusion against the carried manifest, and separately hashes exact supplied document bytes to compare their digest. Report format, document, batch inclusion and anchor results separately. The anchor result is always unavailable in this profile. Do not infer timestamps, source identity or policy satisfaction.

The CLI requires explicit `create --unanchored --representation original|derived` to generate a local single-leaf package. Existing destinations are never overwritten, including symlinks. Package files are written with owner-only permissions (0600) through a completed temporary file and an exclusive hard link. Filesystems without hard-link support produce an error. This is local creation, not transactional service ingestion or a backup/restore guarantee. Repeated creation generates fresh nonces; service retry idempotency is still future work.

There is no revision chain or provider receipt layout yet. Preserve existing packages as immutable bytes. A future anchored profile must have a distinct reviewed version and explicit provider/trust semantics; do not reinterpret this profile's zero-anchor packages as authenticated evidence. An attacker stripping provider material can never obtain default CLI success because default verification requires anchor authentication.

[Python fixtures](../pkg/proof/testdata/unanchored-v1.json) independently reproduce the package byte layout and non-power-of-two paths. They are synthetic and contain no real publications. External protocol review, authenticated receipts and the broader envelope requirements remain open in #3/#4.
